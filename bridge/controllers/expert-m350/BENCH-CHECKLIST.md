## ⛔ SAFETY — applies to every project

1. ⛔⛔ **NEVER run `MGETDATA`.** REFUTED on this firmware — it wedges the controller's *analyzer* (not the
   serial link) and forces a reboot. `FINDINGS.md → find "MGETDATA` = REFUTED"`. No slave configuration fixes it. If a step seems to
   want it, the step is wrong — stop and say so.
2. ⛔ **Nothing here starts the spindle.** The gateway's op allowlist is `{"delete"}` only — it never runs
   or starts G-code. Where a program must *run*, a human at the machine presses Start having checked the
   tool and workpiece. Keep it that way.
3. ⚠ **E-stop within reach for project 3** — it runs a real program.
4. ⚠ **Reboot the controller after any `#279` / serial / network parameter change.** The panel's "Restart
   takes effect" note is real; the port stays silent until you do.

## ⚠ THE CONSTRAINT THAT WILL BITE YOU

**Modbus SLAVE mode and POSITION-POLL mode use the SAME serial port and are MUTUALLY EXCLUSIVE**
(`config.py:37`, `bridge.py:67-69`). Both tasks live in project 3 for exactly this reason — run one, record
it, stop the bridge, run the other. Running both and concluding "tracking is broken" is a **configuration
collision, not a defect**.

## ⭐⭐ STEP ZERO — GET THE CURRENT BUILD ONTO CNC-FAIRY, AND KNOW WHAT THE UPDATE LOOKS LIKE
*(added 2026-08-19, after this checklist was first written. Do this BEFORE the preflight.)*

**Current release: `V2026.08.19.1`.** CNC-FAIRY's exe is almost certainly older, and several fixes since
then matter directly to what you are about to test.

### ⚠⚠ THE UPDATE WILL PROBABLY APPEAR TO HANG. THAT IS EXPECTED. DO NOT PANIC-DEBUG IT.
Every exe built before `V2026.08.18.1` carries a **broken relaunch**: it downloads the update, verifies the
checksum, swaps the binary correctly — and then sits on **"Updated — restarting…" forever**. The fix is *in*
the version you cannot cleanly install, which is the one upgrade where this bites.

⇒ **If it hangs: close DDCS Studio and open it again.** The swap already succeeded, so you come back on the
new version. Nothing is broken and nothing needs reinstalling.
*(Root cause, for reference: `Popen` handed the new process the parent's PyInstaller bootloader vars, so a
onefile child concluded it was already unpacked and died. Fixed with an env-scrubbed relaunch plus an
honest verify — from this build onward a failed relaunch tells you the real reason instead of hanging.)*

⚠ **If you would rather not risk it mid-session, download the exe directly from the release page instead of
using the in-app update.** A clean download has none of this.

### WHY THE BUILD MATTERS TO THIS BENCH SESSION SPECIFICALLY
Three fixes since the checklist was written change what you will see at the machine:

- ⭐ **Flush-left `N`-labels** (t2070). The Expert **rejects an indented `N`-label** — bench-confirmed by a
  controlled A/B on this very machine. Before that fix, **every looped op** (surfacing, pocket, contour,
  holecycle, slot, drill, bore) emitted indented labels inside loops and failed on the controller. ⇒ **A
  program generated by an OLD build may fail to run while the same wizard on the new build works.** If you
  test with a previously-exported `.nc`, that is a plausible cause and not a new defect.
- **Inline `IF … THEN` replaced by `IF … GOTO`-skip** (t2070) — the Expert rejects the inline form.
- **The off-by-500 WCS read** (t2067). "Pull from controller" was reading `setting[macro#]` instead of
  `setting[macro# − 500]`, so a taught G54 came back as `0`. ⇒ **If you pull settings, an old build will
  show zeros that the new one reads correctly.** Do not conclude the controller has lost its offsets.
