**Scope:** 10 readers over the complete `Docs/` pack, adversarially verified. 185 findings survived; 5 claims were killed as wrong and are excluded. ## 1. The headline

### 1.1 Studio's work↔machine frame equation is missing two of five terms, and it is wrong on exactly the machines Studio's own ATC suite creates

The vendor states the identity in full (`Docs/最完整的M350坐标换算公式/Coordinate system offsets DDCSE.txt`), verbatim:

```
#852 = #882 - #807 - #1430 - #837 - #900
       mach   G54     T-off   G52    H-len
```

Studio uses **one** term. `viz/sceneFrame.js:66 wcsOffsetAt()` returns only `{x,y,z}` from the WCS table row, and `engine/envelopeCheck.js:113` is literally `const mach = (workPt[ax]||0) + (wo[ax]||0)`. Three terms are absent everywhere in engine code: **G52** (`#835–#839`), the **per-tool T offset** (`#1390`/`#1410`/`#1430` + `[#1300-1]`), and the **H tool-length** table (`#900–#915`, settings `#400–#415`, 16 slots — `default_vars.js` lists them but nothing reads them).

That defect propagates into two emit paths:

* **`wcsZeroAtCurrent`** (`wizards/dialects/ddcs-expert-m350.js:119-134`) emits `#150=#578` / `#151=805+[#150-1]*5` / `#[#151+2]=#882` — i.e. literally `#807=#882` for G54/Z. The vendor names this exact form as the wrong way to zero: *"Then the command #807=#882 will set not \"0\" for the Z axis in G54, but \"25\"."* (worked with T1 Z offset = −25 mm).
* **The probe wizards' `wcswrite` atom** (`wizards/ops/wcsIndirect.js:36-42`, shared by `cornerWizard.js:161`, `edgeWizard.js:50`, `middleWizard.js:125`) builds `[#1927-#6]` — trigger minus stylus radius, again with no tool-offset term.

The documented correct forms:

```
X:   #[805+[#578-1]*5] = #880 - #[1390+[#1300-1]]
Y:   #[806+[#578-1]*5] = #881 - #[1410+[#1300-1]]
Z:   #[807+[#578-1]*5] = #882 - #[1430+[#1300-1]]
4th: #[808+[#578-1]*5] = #883        (no tool offset exists for 4th/5th)
5th: #[809+[#578-1]*5] = #884
```

`#1430+` becomes non-zero precisely when the operator uses fixed-probe tool setting or ATC auto-measure (`#1305=1`) — Studio's own power-user population. **Honest caveat:** the vendor's "correct" formula still omits `#837` (G52) and `#900` (H), so it is exact only when those are zero. The controller's own UI shortcut, *Monitor → Clear → Clear Z*, already does the tool-compensated form.

Two independent sources confirm the common/G52 offset is silently writable by the operator: system manual §6.4.1 `工件坐标 = 机械坐标-工件偏置-刀具偏置-公共偏置`, and the 加深/抬高 buttons write 公共偏置 in 0.01/0.10/0.50/1.00/5.00 mm steps.

### 1.2 Every CAM pack Studio deploys uses a filename and a folder the vendor spec does not describe

`Docs/自定义CAM/Custom CAM.pdf` is the only vendor spec for the CAM slot format, and it is explicit on all three artefacts going to **three different destinations**:

| Artefact | Vendor path | Vendor name |
|---|---|---|
| icon | `install\CAM` | `cam10.bmp` … `cam19.bmp` |
| parameters | `Install\eng`, `Install\chs` (single **files**) | merged into eng/chs |
| slot macro | `/local` (root) | `cam10.nc` … `cam19.nc` |

Studio writes `CAM/macro_cam22.nc` (`macrosApp.js:1936`) and stamps `( macro_cam22.nc — … )` (`slotPack.js:77`), and its README (`macrosApp.js:1920-1923`) tells the user to copy the whole `CAM/` folder to local — so the file lands at `/local/CAM/macro_cam22.nc`, **wrong on both name and folder**. Corroborating the vendor name from three more angles: the dispatcher parameter is `#968 -p0 -a3 -t0 -s1"NC file index No." -s2"camxx.nc" -m18 -min=0 -max=9999` with `-s3"0-9999:cam0-cam9999.nc"` — and that identical line is in the **user's own live firmware** (`SYSDISK/eng`, not just the vendor sample); the controller screenshot's title bar reads `cam10.nc`; the vendor's own Notepad shot is `cam10.nc - 记事本`. In the 2026-07-31 SYSDISK dump there are no `macro_cam*.nc` and no `camN.nc` at all, and the root is flat (no `CAM/` subdirectory) — icons sit at SYSDISK root as `cam0…cam8, cam10…cam12, cam39 .bmp`.

`macro_camN.nc` comes only from community packs (`references/example-macros/`, `bridge/controllers/expert-m350/assets/cam-menu/CAM10-CAM21/`). Note that even those community packs' own eng comments read `; --- cam14: Inner Corner ---`.

Related deploy defects, same feature:
* **`mergeEng` appends after the file's terminating `&&`.** `slotPack.js:160-161` does `replace(/\s+$/,'')` then appends — the controller eng ends with `…-s3"…"\r\n` + six blank CRLF lines + `&&\r\n`, both `&&` lines confirmed present. It also injects a `( ===== merged CAM pack params (DDCS Studio) ===== )` line into a format with **no comment syntax** (line-start histogram of the real eng: `#` 585, `-` 390, blank 199, `&` 2, space 1 — zero `(`), and joins with bare `\n` into a file that is **1176 CRLF, 0 bare LF**. That `&&` is an end marker is INFERRED — the vendor format doc never mentions `&&`.
* **The allocator starts at `#1100`, which the stock eng already occupies.** The live SYSDISK eng ships `#1100`–`#1102 -m30` and `#1103`–`#1105 -m31` as placeholder rows. `slotPack.nextParam()` starts at `POOL_MIN = 1100` and `usedParams()` only walks the pack's own slots, never the controller's eng — so the first slot a new user builds collides.
* **`baseSlot: 22` is outside anything the vendor tabulates.** The PDF tables run CAM1→cam10/m30 … CAM10→cam19/m39. **Weaken:** the PDF never states 10 is the maximum, and the vendor's own CAM picker screenshot has a scrollbar sized for ~22+ entries; community packs run CAM10–CAM21 (m30–m41) and a stray `cam39.bmp` exists. So slot 22 is *undocumented*, not proven impossible.
* **Only `eng-additions.txt` is emitted; `chs` is never produced.** A Chinese-language controller shows blank labels for every Studio field.

CONFIRMED and correct as built: `POOL_MIN=1100, POOL_MAX=1499, MIRROR=1500` (vendor: *"Parameter number range 1100-1499; Macro address: #2600-#2999"*), `slotGroup = slot+20` (CAM1→m30, CAM10→m39), and the icon format `360×180, 24bpp, BI_RGB, 54-byte header, bottom-up, no palette, xppm/yppm 3780` (parsed from the vendor's own `cam10.bmp`: 194454 bytes, 1080-byte rows, no padding).

### 1.3 Rigid tapping emits no `M180` and no `M29` — the G84 likely runs against an unsynchronised analog spindle

`Docs/G83_G84钻孔攻丝指令说明/G84测试.txt`, complete file:

```
M180  //切换到伺服主轴
M29 S2000  //刚性攻丝模式
G00 X10 Y0 Z2
G98 G84 X10 Y0 Z-10 R2  F2000  //G84攻丝 螺距1mm=S2000/F2000
M30
```

`wizards/ops/tap.js:22-31` rigid branch emits `M3 S<rpm>` / `G84 Z R F` / `G80` / `M5`. Grep confirms `M29`, `M180`, `M181` appear **nowhere** in `DDCS-Studio/web`. The G/M list corroborates independently: `M29 | Replacement G95. Synchronizes the rotation of the servo spindle with the movement of the Z axis, for G1 commands. G0 is not synchronized. Doesn't work from MDI. M5 is cancelled.`; `M180 Enables servo spindle mode`; `M181 Enables analog spindle mode`; and G74/G84's own rows say *"Works in conjunction with M29."*

Feed is the one thing Studio gets right: `feed = rpm * pitch` matches the vendor's `螺距1mm = S2000/F2000` exactly.

**Prerequisites are machine-side and readable, not a checkbox.** Vendor setup doc: `Pr080` = servo-spindle channel select (e.g. 4th axis), `Pr006` = that axis's pulses per spindle revolution, `Pr007` = pulse dimension (pulses/degree), plus **an assigned output port** for the M180/M181 mode switch. Verification test: MDI `G91 G01 A1` → one full spindle revolution. **Correction to the reader's proposal:** `Pr080 != 0` is *not* a valid gate — the eng declares `#80 … -s1"Spindle mapping axis" -min=0 -max=5 -i0"X-axis" -i1"Y-axis" …`, so 0 = X-axis. The readable signal is `#79 … -s1"Spindle interface type" -i0"Analog" -i1"Plu/dir" -i2"Multi-speed"`, and `data/dumpImport.js mapSpindle()` **already reads both** into `spindle.interface` / `spindle.mappingAxis`. Also note: emitting M180/M181 blind is not automatically safe if no output port has been assigned.

⚠ **Unresolved contradiction in the vendor's own setup doc:** it says `Pr007 = 脉冲/度` (pulses per *degree*) but its verification test is `G91 G01 A1` → *one full revolution*. A1 cannot be both. Do not encode either reading without a bench check.

⚠ `#1620=0` **requests a start**. Anything that can write it can start an unattended machine. Never write `#1620`–`#1626` from the gateway. **Weaken the reader's claim** that this is "reachable over Modbus": the Modbus manual documents the M350 as **master only** (`Master-slave mode: Default master mode`), and its macro surface is the MGETDATA/MSETDATA data buffer, limited to `#50–#499`. Nothing in the pack exposes macro addresses to an external master. Remote run control, if it exists, is the *slave* register path (project memory, unverified: write `6908` keypress, read `10002` state) — not `#1620`/`#1630`.

### What remains as a progress mechanism, ranked

1. **`RECORD[]` → `/local/RecordDataN.txt` — the strongest candidate.** `RECORD[x1..x7]`; `x1` function code (`−2` flush cache to file, `−1` clear cache, `0` store to cache, `>1` user format via msg1), `x2` file index (`=3` → `RecordData3.txt`), `x3–x7` data. *"Notice: file path is /local"*, *"Software version: 2022-05-25-00 and the latest"*. `/local` is exactly what the gateway already reaches over the share — no Modbus, no serial wiring, no listener. ⚠ The **Chinese twin in the same folder documents an older, smaller spec** (`−1` clear, `0` save; only `X3-X6`), so the cache-then-flush pattern is firmware-gated. Flash-write cost is uncosted.
2. **The existing beacon — but understand its transport.** `MGETDATA`/`MSETDATA` *"Requests/Transmits data via RS232 port No. 2"* and the controller is the Modbus **master**. **A LAN/Modbus-TCP listener can never answer, ever.** A beacon listener must be an RTU slave on RS232 port 2 (there are two independent RS232 ports on the DB9 — `2 RXD1 / 3 TXD1 / 5 GND1` and `7 RXD2 / 8 TXD2 / 9 GND2`; the pack contradicts itself on whether pin 9 is GND1 or GND2). Also note `instrument.js` already records that the 1–2 s figure was a **V4.1-with-no-Modbus timeout measurement on a path that is now gated shut** — it is not the live Expert cost, which is stated as one synchronous serial round-trip.
3. **`#1503` on-screen status — human-only, zero cost, no readback.** Gated on `Pr269 "Debug printing enable"` (`-p0`, operator-writable, `-i0"No" -i1"Yes"`). Studio already ships this as the `hmistatus` atom.
4. **`#1750–#1799` trigger+poll serial API.** The vendor's `O10105` listing shows `#1760` buffer var, `#1761` port, `#1762` slave id, `#1763` register, `#1764` byte count, `#1765` function selector, `#1769` trigger/busy, `#1766` return code, `#1770–#1775` byte↔number converter (`#1773`: 1 = int16 signed, 4 = uint32). ⚠ **"Non-blocking" is INFERRED from the shape of the vendor's own hand-written `WHILE [#1769 NE 0] DO2` loop — nowhere stated.** The macro table says only *"Modbus function macro address"* for all 50 slots, with no timing contract. The one worked example is an encoder read on **port 0**, not port 2.
5. **`#884 = #<var>` DRO trick.** *"you write the command \"#884=#1430\" in MDI … the machine position of the 5th axis will change to the value"*. ⚠ Hazardous and weakly useful: the same paragraph says this *"is equivalent to performing the homing procedure"* — it re-datums that axis **and marks it homed**. Only safe on an axis the machine does not have, and reading it back still requires the unverified slave-register map.
6. **`Pr269` debug output over serial** — pure lead. What it prints is documented nowhere. Cheap bench test: `Pr269=1`, open Serial 1 at B115200, run a program.

**Do not keep hunting for a line-number variable.** Point the next effort at (a) whether `Pr283 "Barcode scanning processing"` or the slave register map exposes `Cur No.`, and (b) costing `RECORD[]`.

### Beacon frame (from the Modbus manual — the reader's claim it sat in was rejected, but this correction is verified)

`MSETDATA[X1..X6]`: **X1** = first macro var, **must be 50–499**, one **byte** each; **X2** slave id; **X3** start address; **X4** = **byte length** (*"one register occupies 2 bytes"*), coils = coil count; **X5** function-code selector (03→3, 04→4, 0F→15, 10→16); **X6** = **the macro address (50–499) where the exception code is stored** (`0x00` normal, `0x0B` no response, `0xFF` timeout) — **not a timeout value**.

Therefore Studio's `MSETDATA[250,1,0,2,16,300]` writes **one** holding register (2 bytes) at address 0, with `#250` as the **low** byte and `#251` as the **high** byte — not two registers — and `#300` is already an available error channel. "Lowering the 300" would set an out-of-range macro address and shorten nothing.

All other decodes check out (X± 0x015e/0x015f, Y± 0x0160/0x0161, Z± 0x0162/0x0163, 4th± 0x0164/0x0165, Start 0x0148, Pause 0x0149, Reset 0x0147, High/Low 0x0184). ⚠ There is **no Modbus keypress path in Studio's source** — `6908` appears nowhere outside the memory note; the reader's claim that Studio "writes register 6908" is false.
* **The `Pr279` vs `Pr779` scare is void.** They are the same thing: parameter Pr279 mirrors at macro `#779`. The macro-table neighbourhood proves it (`766` Serial 1 baud, `767` Serial 2 baud, `769` Debug printing enable, `778` USB keyboard type, `779` *"Modbus RTU (The Barcode processing file storage)"*, `780/781` accel, `783` Barcode scanning processing, `784` network boot mode = Pr266/267/269/278/279/280/281/283/284 + 500). That row also **corroborates** the Modbus-slave memory rather than contradicting it: the number is stable, the *meaning* was extended by firmware.
* **`#1302` is the magazine TYPE, not a boolean enable.** `atcInterpreter.js` should branch on `0/1/2/3/4`, not treat `>0` as on.

### Documents that contradict each other — do not treat either as authoritative alone

* **Pr850–Pr865 / Pr870–Pr885.** The manual calls them `H01-H06 偏置值` and `D01-D16 偏置值`. The **live eng file settles it against the manual**: `#850 "T01 Y mach pos"` … `#865 "T16 Y mach pos"`, and `#870 "T01 Z mach pos"` … `#885 "T16 Z mach pos"`. Do not propagate the manual's H/D reading. (Also note the manual's own internal typos: the `0930-0944` row is labelled Z in the name column and Y in the description, and `0850-0865` is 16 slots labelled "H01-H06".) Pr930–**945** (16 tools) is right; the manual's 0930-0944 is off by one.
* **T17–T20.** The **Chinese** macro table documents 24 rows the EN table leaves blank: `#1346-1349` X mach pos, `#1366-1369` Y, `#1386-1389` Z, `#1406-1409` X offset, `#1426-1429` Y offset, `#1446-1449` Z offset — consistent with `#1300 "Current tool No. [0-20]"`, `#1301 "Total number of tools [0-20]"` and `#1970-1989`. But the **captured eng stops at T16** (`#945 "T16 Z offset"`, `#945` last). ⚠ **Unresolved.** No Studio action needed — `default_vars.js` already carries 1346–1349 and `atcGenerator` has no 16 cap — but record the conflict before anyone adds one.
* **Pr488–Pr492 axis encoding** (gantry) — see §4.
* **Pr127 / `#1992` power-on homing polarity.** `#627 "Home after booting 0: Yes; 1: No"` vs the homing doc's `IF #1992 == 0 GOTO2` placed *before* the homing calls (0 ⇒ skip). The Chinese word is 提示 (*prompt*), so Pr127 may govern a power-on prompt while `#1992` governs whether the search runs. ⚠ **Do not display or write Pr127 with a Yes/No label until confirmed.**

The G/M sheet claims `M98`/`G65` use `#1–#17` (the same list shifted +1) and G65's own row says *"Transfers the number 5 to variable #1"*. The pack does not adjudicate. ⚠ **Anyone writing an O-subroutine must verify which convention its entry point uses.** (The reader's supporting claim that Studio's probe path calls `M98P502` and its ATC path `M98P20000` is **false** — grep shows only `homingWizard.js:78 M98P501X<n>` is real.)

### Deploy / gateway

* `install/` is a documented hook set, but **not all of it is editable**: `error.nc`, `cmdstr`, `rcS`, `smb.conf` are marked **禁止修改！**; only `sysstart.nc` is explicitly marked **可修改！**. `slib-g.nc` implements **G53, G81, G82, G83, G84, machine homing, tool setting and the magazine as macros** — so canned-cycle behaviour is a per-machine post capability, not a constant.
* Studio's `T.nc` generator (`atcGenerator.generateToolChangeNc`, declared in `controllerFiles.js:33`) **overwrites the one-line dispatcher** `T#1504` and therefore bypasses `O20000`'s entire magazine state machine (`#1302` dispatch, dust cover, magazine open/close, per-tool Z, auto tool-setting, position restore). Either write into `slib-g.nc`/`O20000` or warn loudly.
* SMB: the vendor requires **SMB 1.0/CIFS Client AND Server** ticked in Windows Features and a PC reboot, on Windows 11. ⚠ *"SMB 1.0/CIFS Automatic Removal"* is visibly unticked in the vendor screenshot but the doc never mentions it — Windows uninstalling SMB1 after ~15 idle days is an **inferred** (but very plausible) cause of the intermittent "gateway can't see the controller" class.
* Share must be named **`share`** (lowercase) — but the name lives in **UI string `#806` of `msg`/`msg1`/`msg2`**, not a parameter, so make it configurable with `share` as the default. ⚠ For a `Pr240=3` controller the vendor never says where the share name comes from (`msg_utf8` is not mentioned).
* Vendor procedure shares to **Everyone / Read-Write**, and no credential field exists in the documented flow. ⚠ *"The controller authenticates as a guest"* is **inferred** — the doc simply never mentions authentication, and the System Set menu does include a `Load WPA Config` item, so credentials are not universally absent from the device.
* `Pr284 "Network boot mode"` = `0 Close / 1 auto-IP / 2 manu-IP`, `-p1` (Administrator), restart required. Host IP is set in **F4 → System Set → Set IP Addr → Host IP Addr**. Documented gotcha: *"If access is not successful after switching, please press the disk switch button one more time!"* — the mount is lazy and the first attempt is expected to fail. Known-good baseline: software `2024-09-10-01`, hardware/firmware `2021-1213-30`. ⚠ The System Info screen labels as **"Hardware Ver"** what the checklist calls **firmware**.
* Keep generated `.nc` filenames **ASCII** — the language doc warns non-English characters in file names may render wrong even on a properly localised unit. Also: local disk free space in the vendor self-test reads ~806 MB, so large toolpaths belong on NetDisk.
* K-key binding: `K1–K7 = Pr210–216`, `K8–K10 = Pr217–219`, `K11–K14 = Pr231–234`, `K15 = Pr251`, `K16 = Pr252`, all `-min=0 -max=2000`. Value `0` runs `key-xx.nc`; `1–32` toggles an output; `>1000` is a function shortcut. **1399 = CAM page** (confirms the existing memory), **1391 = NetDisk** (a one-press jump to the gateway share — worth adding to setup instructions), **1396 = barcode input box**. ⚠ 1396 is **absent from the vendor's own K-code table**, which jumps 1391→1399 — so that table is **not exhaustive**; do not validate K assignments against it. ⚠ The `key-xx.nc` numbering (whether `xx` tracks the K number or the parameter number, zero-padded or not) is **specified nowhere in the entire pack** — resolve on hardware before authoring these.
* External-key macros need **all three** files per button: `extnc1-N.nc` (short press), `extnc0-N.nc` (**release**), `extnc2-N.nc` (keep press). The unused two **must exist** — the vendor's filler is literally `G90 G54`. This requirement exists only as the *filename* of a 0-byte file in the pack and is absent from the English PDF. ⚠ Delivery path is ambiguous: *"place them in the upgrade package named [install] in the folder for upgrade"* parses two ways. ⚠ External-key macros are **inert while a program runs**, so they cannot be a mid-cycle interlock. ⚠ A **latching** switch on an extern-key input makes the **entire keyboard stop responding** (Chinese-only warning; the English PDF states the requirement but not the consequence).

`vendorx.py` (a) mis-aligns sparse rows in these `.xlsx` files by dropping empty leading cells, and (b) **does not extract `xl/drawings/drawing1.xml`** — which holds **35 text boxes containing the factory `slib` source code**, roughly half the value of `G-M-code full list.xlsx`.
